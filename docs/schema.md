# agent-brief-me: inbox schema and protocol

This document is the authoritative schema for the two JSONL files that make
up the inbox: `~/.agent-brief/inbox.jsonl` and `~/.agent-brief/answers.jsonl`.
Every tool that reads or writes these files (skills, `scripts/dispatch.py`,
tests) must follow the rules below.

## Storage

| File | Holds | Record types |
|---|---|---|
| `~/.agent-brief/inbox.jsonl` | questions, reports, and their status changes | `question`, `report`, `status` |
| `~/.agent-brief/answers.jsonl` | answers to questions | `answer` |

Both files are **append-only**: a line, once written, is never edited,
reordered, or deleted. Current state is never stored directly; it is always
derived by folding the file from the first line to the last (see
"Deriving current state" below).

Each line is one UTF-8 JSON object followed by a single `\n`. Empty lines do
not occur; readers may skip a blank trailing line at end-of-file.

### Record discrimination

`inbox.jsonl` interleaves three different shapes on the same file, so every
record in `inbox.jsonl` carries a `"type"` field whose value is one of
`"question"`, `"report"`, `"status"`. This is the only field not called out
in the acceptance field lists below; it exists because a reader folding
`inbox.jsonl` line by line must know which schema to validate a line against
before looking at its other keys. `answers.jsonl` holds exactly one shape
(`answer`), so its records carry no `"type"` field.

### IDs

Every `id` (on `question` and `report`) is a UUIDv4 string, generated by the
tool that performs the write (never supplied by the caller). UUIDv4 draws
from a 122-bit random space, so ids stay unique across independent,
concurrent writers without any coordination between them. Generate with
Python's stdlib: `str(uuid.uuid4())`.

## Record types

### `question`

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "question",
  "type": "object",
  "properties": {
    "type": { "const": "question" },
    "id": { "type": "string", "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$" },
    "project": { "type": "string", "minLength": 1 },
    "title": { "type": "string", "minLength": 1 },
    "body": { "type": "string" },
    "choices": { "type": "array", "items": { "type": "string" } },
    "multi": { "type": "boolean", "description": "true when more than one choice may be picked; the answer's chosen is then an array. Default false." },
    "recommendation": { "type": "string" },
    "severity": { "type": "string", "enum": ["low", "normal", "high"] },
    "created_at": { "type": "string", "format": "date-time" },
    "session_id": { "type": "string", "description": "Claude Code session that submitted this; reopen with `claude --resume <session_id>` in the project directory. Optional." }
  },
  "required": ["type", "id", "project", "title", "body", "severity", "created_at"],
  "additionalProperties": false
}
```

Example:

```json
{"type": "question", "id": "d3db7eab-59ec-436d-b2d4-ad2928328a48", "project": "agent-brief-me", "title": "Which datastore for the inbox?", "body": "SQLite gives us indexing but adds a dependency; append-only JSONL needs no dependency but folds state at read time. Which one?", "choices": ["SQLite", "JSONL"], "recommendation": "JSONL", "severity": "normal", "created_at": "2026-08-20T09:00:00Z"}
```

### `report`

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "report",
  "type": "object",
  "properties": {
    "type": { "const": "report" },
    "id": { "type": "string", "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$" },
    "project": { "type": "string", "minLength": 1 },
    "summary": { "type": "string", "minLength": 1 },
    "severity": { "type": "string", "enum": ["low", "normal", "high"] },
    "created_at": { "type": "string", "format": "date-time" },
    "session_id": { "type": "string", "description": "Claude Code session that submitted this; reopen with `claude --resume <session_id>` in the project directory. Optional." }
  },
  "required": ["type", "id", "project", "summary", "created_at"],
  "additionalProperties": false
}
```

Example:

```json
{"type": "report", "id": "f00c2a4c-e50a-4268-a56f-e4894386ddb8", "project": "agent-brief-me", "summary": "F1 schema and concurrency smoke test done; both files documented.", "severity": "low", "created_at": "2026-08-20T09:30:00Z"}
```

### `status`

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "status",
  "type": "object",
  "properties": {
    "type": { "const": "status" },
    "ref": { "type": "string", "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$" },
    "status": { "type": "string", "enum": ["answered", "cancelled", "read", "reopened"] },
    "at": { "type": "string", "format": "date-time" }
  },
  "required": ["type", "ref", "status", "at"],
  "additionalProperties": false
}
```

`ref` is the `id` of the `question` or `report` this status line applies to.
`answered`, `cancelled`, and `reopened` apply to questions; `read` applies
to reports.

Example:

```json
{"type": "status", "ref": "d3db7eab-59ec-436d-b2d4-ad2928328a48", "status": "answered", "at": "2026-08-20T21:00:00Z"}
```

### `answer`

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "answer",
  "type": "object",
  "properties": {
    "question_id": { "type": "string", "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$" },
    "chosen": { "oneOf": [ { "type": "string" }, { "type": "array", "items": { "type": "string" }, "minItems": 1 } ], "description": "one choice, or an array when the question has multi: true" },
    "free_text": { "type": "string" },
    "answered_at": { "type": "string", "format": "date-time" },
    "consumed": { "type": "boolean" }
  },
  "required": ["question_id", "answered_at", "consumed"],
  "additionalProperties": false
}
```

`question_id` is the `id` of the `question` in `inbox.jsonl` this answer
responds to. At least one of `chosen` or `free_text` is expected in
practice, but the schema does not force it since a free-text-only or
choice-only answer are both valid.

Example:

```json
{"question_id": "d3db7eab-59ec-436d-b2d4-ad2928328a48", "chosen": "JSONL", "free_text": "no external dependency wins", "answered_at": "2026-08-20T21:00:00Z", "consumed": false}
```

## Deriving current state

Nothing is stored as mutable state; every reader recomputes it by folding
the file in order:

- **Question state**: find every `status` line with `ref` equal to the
  question's `id`. If none exist, the question is `pending`. Otherwise the
  question's state is the `status` field of the *last* such line
  (`answered`, `cancelled`, or `reopened`). A last line of `reopened` folds
  the question back to `pending`: it reappears among pending questions and
  can be answered or cancelled again, any number of times.
- **Report read state**: find every `status` line with `ref` equal to the
  report's `id` and `status == "read"`. If at least one exists, the report
  is read; otherwise it is unread.
- **Answer current value**: find every line in `answers.jsonl` with
  `question_id` equal to the question's `id`. The current value, including
  `consumed`, is the *last* such line. (A later line with the same
  `question_id` is how `consumed` flips from `false` to `true` once the
  answer has been picked up: append a new line with the same fields and
  `consumed: true`; never edit the earlier line.)

## Lifecycle

- A `question` starts `pending` the moment its line is appended.
- It becomes `answered` or `cancelled` by appending exactly one `status`
  line with `ref` equal to its `id` and the corresponding `status` value.
  A `cancelled` question can be reopened by appending a `status` line with
  `status: "reopened"`, which folds it back to `pending` (see "Question
  state" above) so it can be answered or cancelled again. `answered` is
  terminal; `cancelled` can return to `pending` via `reopened`.
- A `report` starts unread and becomes read by appending a `status` line
  with `ref` equal to its `id` and `status: "read"`.
- An `answer`'s `consumed` flag starts `false` and becomes `true` by
  appending a new `answer` line for the same `question_id` (see above).
- No record of any type expires automatically. There is no time-based
  transition; a `pending` question or an unconsumed `answer` stays that way
  until an explicit status/answer line changes it.

## `dispatches.jsonl`

Written only by `scripts/dispatch.py`; append-only like the other files.
`--watch` dispatches also pre-accept the one-time workspace trust dialog by
flipping `hasTrustDialogAccepted` to `true` for the project in claude.json
(default `~/.claude.json`, overridable via `BRIEF_CLAUDE_JSON` for testing);
headless (`-p`) dispatches never touch claude.json. Two shapes, discriminated
by `type`:

```json
{"type": "started", "batch_id": "<uuid4 shared by one dispatch.py run>", "project": "my-project", "pid": 12345, "started_at": "2026-08-22T01:02:03Z", "log": "/path/to/logs/my-project-<hex>.log", "tasks": ["Which datastore for the inbox?"]}
{"type": "finished", "batch_id": "<same uuid4>", "finished_at": "2026-08-22T01:20:00Z", "exit_codes": [0, 0]}
```

`log` is `null` for `--watch` windows. `tasks` is the question `title` of
every unconsumed answer this dispatch consumed for that project, in the same
order as the prompt (empty array if none). Records written before this field
existed have no `tasks` key; readers must treat a missing `tasks` as `[]`,
never error on it.

A project is *running* when it has a `started` line whose batch has no
`finished` line and whose `pid` is still alive (unknown counts as alive);
`GET /api/state` exposes that as `running: {project: {started_at,
elapsed_seconds}}`, plus a `sessions: {running: [...], finished: [...],
finished_hidden: N}` field (running/finished session details, `tasks`
included; `finished_hidden` is the session count older than the 7-day
`finished` window) - see F14's acceptance in `feature_list.json`/
`docs/archive/features.jsonl` for the exact per-session shape.

A running session ends in one of two ways (`ended_by` on each `finished`
element): `exit` - the batch waiter wrote a `finished` line; or `report` - a
report for the same project was filed to `inbox.jsonl` with `created_at` at
or after the session's `started_at` (F15). The report rule exists because a
`--watch` claude window stays alive at its prompt after the work is done, so
pid liveness alone would show it running forever. A report-ended session has
`finished_at` = the earliest such report's `created_at` and `exit_code: null`.

## Atomic append rule

- One record is exactly one line: a single JSON object, UTF-8 encoded, with
  no embedded newline, followed by one `\n`.
- The encoded line (JSON body plus the trailing `\n`) must not exceed 8192
  bytes (8 KiB). A writer must check this before attempting to append and
  must refuse to write a record that would exceed it.
- The file is opened in append mode, and the write is a single OS-level
  `write()` call carrying the whole line, made while the writer holds an
  exclusive lock on the file:
  - POSIX: `fcntl.flock(fd, fcntl.LOCK_EX)` on the append-mode file
    descriptor.
  - Windows: `msvcrt.locking(fd, msvcrt.LK_LOCK, 1)` on a 1-byte sentinel at
    offset 0 of the same file (this works even on a file smaller than 1
    byte).

  The lock is released immediately after the write completes. Holding it is
  what makes the append atomic: neither platform's plain "open with append
  flag" guarantees that a `write()` from one file handle cannot interleave
  with a `write()` from another independently-opened handle to the same
  file once lines are larger than a few hundred bytes, and on Windows this
  interleaving is observable even for short lines, because the platform's
  append-mode seek-then-write is not atomic across handles the way POSIX's
  is under `PIPE_BUF`. The lock removes the race regardless of platform or
  line size (up to the 8 KiB cap).
- This is exactly the rule `tests/test_concurrent_append.py` implements in
  its `atomic_append_line()` helper, and the concurrency smoke test is the
  executable proof that it holds: 5 threads append 20 `question` lines each
  to the same `inbox.jsonl`, and the test asserts the file ends with
  exactly 100 valid, uniquely-`id`'d lines.
